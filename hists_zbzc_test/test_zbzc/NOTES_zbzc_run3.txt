FLAVOUR LABELLING (MC generator truth)
--------------------------------------
From FatJet_nBHadrons / FatJet_nCHadrons of the leading AK8 jet (hadrons
ghost-associated to the jet). First match wins:
    bb : >= 2 B hadrons
    b  : exactly 1 B hadron
    cc : 0 B, >= 2 C hadrons
    c  : 0 B, exactly 1 C hadron
    l  : 0 B, 0 C (u/d/s/gluon)
    data : real data (no truth available)
b has priority: a jet with a B hadron is b/bb even if it also has C hadrons.
"Generator truth" = what the simulation knows really happened; only exists in MC.
In data we rely on the taggers (Xbb, Xcc); MC truth is used to measure the
tagger efficiency / mistag rate.
Taggers are only histogrammed so far -- no working-point cut applied yet.


FIRST TEST (1 file per sample, low stats)
-----------------------------------------
- Runs end to end, cutflows and SFs sensible (pileup weight mean 1.000)
- ~80-84% of selected jets are light; c+cc ~12% (ee) to ~24% (mumu)
- Yields in yields.txt


WHY Zmm "b" = -191.8 IN yields.txt
----------------------------------
It is NOT a number of events. It is a scaled, weighted yield:
    yield = sum over events of (genWeight x SFs) x xsec x lumi / sumw
i.e. the predicted number of events in 7.98 fb^-1 from these test files.

amc@NLO samples have NEGATIVE generator weights for some events (part of the
NLO calculation; they cancel against positive ones with enough statistics).

Breakdown of Zmm b by sample:
    inclusive : 1 raw event, weight -19502 x scale 0.014   = -273.0
    PTLL-100  : +7.5
    PTLL-200  : +61.9
    PTLL-400  : +11.9
    PTLL-600  : 0
    total     : -191.8

So a single negative-weight event from the inclusive sample (1 file only)
dominates. Each inclusive event carries a large weight after scaling
(~ +/-270 events), and only 8 inclusive events passed the full Zmm selection
(inclusive covers LHE pT(ll) < 100, so a 200 GeV AK8 jet is rare there).
-> statistical artefact of the 1-file test, not physics. Should go away with
   the full sample. The Zmm light yield from the inclusive sample is also
   negative for the same reason.
Check later: if the inclusive sample still contributes large +/- weights in
the full run, consider how much it matters in the boosted region.


FRAMEWORK BUG (not fixed, shared code)
--------------------------------------
utils/correction.py eleSFs resets the running SF product inside the per-electron
loop -> only the last electron's SF is kept. Our workflow avoids it by calling
the SF function once per lepton. Report to framework maintainers.
